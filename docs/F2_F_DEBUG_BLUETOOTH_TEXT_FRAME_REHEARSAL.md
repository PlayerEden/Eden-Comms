## Proposed plaintext frame format — NOT wire-ready for radio

`DebugBluetoothTextFrameCodec` encodes/decodes ONE complete application
frame intended **only as plaintext inside a future reviewed, live,
authenticated encrypted TLS session**. Never place its bytes directly
on RFCOMM, an unverified TLS session, or a control/probe stream.

| Offset | Length | Meaning |
| --- | --- | --- |
| 0 | 4 | ASCII `ECBT` magic |
| 4 | 1 | version `0x01` (other versions fail) |
| 5 | 1 | type: `0x01` TEXT or `0x02` ACK |
| 6 | 8 | positive, big-endian message ID (`int64`) |
| 14 | 2 | unsigned big-endian payload byte length |
| 16 | 0–512 | TEXT strict UTF-8 only; ACK requires **zero** bytes |

- **TEXT:** 1–512 UTF-8 bytes, nonblank, no NUL, strict malformed/
  unmappable character rejection (no silent replacement).
- **ACK:** exactly 16 bytes including header, zero payload; means
  only *peer application accepted that message ID* once actually
  generated and sent on an authenticated channel. It is NOT a delivery
  receipt generated by local TLS writing, nor a read receipt.
- No extension fields, implicit padding, trailing bytes, scanning,
  partial-frame acceptance, unbounded allocations or fragmentation
  support. Header length and payload length must match exactly.
- This draft protocol has **not been independently reviewed**. Its
  actual use requires explicit review/versioning, TLS record boundary
  handling and live owner authorization. The codec itself neither
  encrypts data nor binds message IDs to a peer.

## Per-session policy (pure deterministic model, unwired)

`DebugBluetoothTextLedger` is one in-RAM model per future session:
- positive local outgoing message IDs starting at 1, monotonically
  increasing; **max 128** TEXT messages per direction;
- at most **8** unacknowledged local messages;
- incoming TEXT message IDs must arrive in exact ascending order;
  duplicate, skipped or replayed messages are rejected;
- unknown, early, duplicate and non-ACK acknowledgements are rejected;
- close permanently blocks future operation and discards pending IDs.
  It intentionally never stores message bodies.

The ledger does not accept a bare `DebugBluetoothProbeCompletion` as
authentication, and it is **not referenced** by the live controller or
probe. Generating a TEXT frame locally does not mean anyone received
it. The future live session owner must preserve the verified engine,
both QR-bound identities and actual final approvals on the same socket
under a reviewed lifecycle; no new authorization claim arises here.
